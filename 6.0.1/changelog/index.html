Edition

Changelog

Each edition of Pauta is a version, numbered as below. The entries come from the repository’s CHANGELOG.md, in Keep a Changelog form. Changes collect there until a batch is ready and then come out together as one edition, so an app moves between editions less often and each move is worth making. While a batch waits, it can be read as Pauta Next, under Unreleased below. Next is not an edition: it has no number, can still change, and an app is never built or audited to it.

How editions are numbered

Section titled “How editions are numbered”

An edition is numbered major.minor.patch. The number says what moving an app to it costs, judged by the rules alone: which rules exist, their levels, and what each one asks. Only what the guide says moves it; how the site shows it never does.

  • Patch (4.1.0 → 4.1.1): an app built to the edition before it does nothing. The guide says the same thing more clearly or more correctly, and no rule’s ID, level or requirement changes: a rule reworded without changing what passes, a wrong fact about an app fixed (the matrix, Gaps per app, a Reference), a Check fixed to test what its rule already asked, a new or replaced screenshot, a page or section that adds no rule.
  • Minor (4.1.1 → 4.2.0): an app adds what the new or stronger rules ask, and undoes nothing. The rules change, but everything that conformed still conforms: a new rule at any level, a level raised (SHOULD → MUST, MAY → SHOULD) or lowered, a rule that covers more cases, a rule retired with nothing in its place.
  • Major (4.2.0 → 5.0.0): an app changes work it already did. Something that conformed must be undone or redone: a rule reversed, or replaced by one that asks for something else; a requirement changed so the old way now fails (a different file name, value, chord, color or layout); a change to what MUST, SHOULD, MAY or “built to an edition” means.
  • No edition: nothing a reader takes as guidance changes, so the number stays and the changelog has no entry. A typo or spelling fix, a broken link fixed or a link added, Markdown and markup, the site’s styles, scripts, build and branding, the PDF’s layout.

The largest change in the batch sets the number: an edition that adds ten rules and reverses one is a major. A new MUST is a minor, even when every app fails it today: an app names the edition it is built to (pauta.version, the About window), so a new MUST asks nothing of it until it moves, and moving adds work without undoing any. Numbers are never reused or changed, since every edition keeps its address; 2.0.0 and 3.0.0 were numbered under an earlier rule that made any new MUST apps failed a major, and under these rules both would be minors.

Added

Reading a rule

  • changed on every rule. In rules.json each rule carries changed: the edition in which its level, its scope (appliesTo) or its statement last changed, 2.0.0 at the earliest. A rule’s Why, Check, Command and Reference can change without moving it; any edit to the statement’s words moves it. An app moving to a newer edition reads again the rules whose changed is newer than its own edition. Editions up to 5.0.0 don’t have the field. The record behind it is rule-changes.json at the repository’s root, which a release rewrites.

Auditing an app

  • A status for what an audit cannot reach. not-checked is for a Check that reads what the app’s checkout does not hold: the website’s repository (DOCS-01 to DOCS-04, PAUTA-13, PAUTA-14), or what GitHub keeps and no file shows (the status checks REL-19 has the default branch require, the issue behind a pending entry in PAUTA-07). Such a Check says so. The audit judges the part the checkout holds first, and that part can fail the rule: an app whose repository and About name no website for its user docs fails DOCS-01, DOCS-02 and PAUTA-13 from the checkout, and not-checked is only for an app that names one. The audit reads the rest when it can (the website checked out beside the app as ../<app>-website, gh signed in), and reports not-checked with what would settle it when it can’t. ABOUT-07 gets the status too, in an audit run against an edition other than the one the app names. It is not a finding and not a pass, needs no exception and blocks no release.
  • By-hand checks, read back. A manual result carries the rule’s entry from the checked list of the app’s pauta.json (PAUTA-18) when there is one: the edition it was checked against, the date, and the app’s version where recorded. With no entry its evidence ends “not recorded”, which is not a failure and needs no exception. An entry whose edition is older than the rule’s changed is stale, and the report says so as a problem. The audit never writes an entry: that is for the person who checked the rule in the running app. A by-hand Check that sends the person somewhere other than the running app, to the repository’s merged pull requests (DOCS-16, PERF-18, PERF-22) or to break a test and watch it fail (QUAL-10), is manual like the rest, never not-checked.
  • Two rules judged last. PAUTA-04 and ABOUT-07 have the audit itself as their Check. The skill judges them after every other rule in scope, from those results; a manual or not-checked result fails neither, and an audit of part of the edition says it judged them from the rules in its scope. Only the rules of the edition the app names settle an About that says Built to: an audit run against another edition reports ABOUT-07 as not-checked and names the edition whose rules would settle it, and an About that says Working toward passes whatever edition was audited. Both were checked by hand in 5.0.0.

Editions and Pauta Next

  • Pauta Next, at next/. While changes wait under Unreleased, the site serves them at https://pauta-project.dev/next/, built from master on every deploy: the pages, the agent files, the Markdown download and the PDF, with the waiting changes under What’s new on its overview. It is not an edition: it has no number or date, is never tagged or archived, is kept out of search engines, and links the apps’ code at their default branches where an edition links pinned commits. The edition switcher and versions.json list next while it exists; with nothing waiting, every address under next/ redirects to latest/.
  • Every file of next/ says what it is. Each page opens with a notice, written into the page’s own HTML so an agent that fetches the page reads it: never cite a rule from Pauta Next or audit an app against it. llms.txt, llms-full.txt, each <page>.md, changelog.md, the audit skill, both schemas, the Markdown download and the PDF’s cover carry the same notice, and rules.json has it in a next field. In next/ a rule new or changed since the last edition has "changed": "next".

Same on every OS

  • OS-04 · MUST. No behavior or layout of an app differs by OS: what a command, a key or a click does, where a control sits and how a window is drawn are the same on Windows, macOS and Linux, except where a row of the table Where the OS’s way wins gives the difference. OS-01 covers only whether a command, setting or window exists, and its default. A place that gives an OS something other than what its row gives is judged by the rule that row links, where that rule covers it: nux’s Windows notification, a tray balloon and not a toast, fails TRAY-09 and not this rule. No app has been read through for it. Found so far: Mirada closes its window on Escape on Linux only, follows the OS’s accent color on macOS and Windows only, puts its title on the left on Windows only and has a menu bar on macOS only; Editora deletes a file for good on Windows, keeps the user’s key bindings apart by OS and registers its WSL targets on Windows only; Termina believes the folder a shell reports for itself on Windows only, and its Settings Sync keeps the user’s key bindings in one file for macOS and another for Windows and Linux.

Conformance

  • PAUTA-18 · MUST. pauta.json may hold a checked list, the record of the rules a person checked by hand in the running app and found met: each entry has the rule, the edition it was checked against and the date, and may have the app’s version. The rule governs only the entries an app records, so an app with no list, or an empty one, meets it. An entry names a rule whose check is by hand, never one that has an exception, and is stale when its edition is older than the rule’s changed in rules.json: the app’s test (PAUTA-10) fails it until it is removed and the rule checked again. No app records a by-hand check yet, so each meets the rule.

Repository documents

  • REPO-11 · SHOULD. Every script in scripts/ is a Java source file the JDK runs as it is (java scripts/Name.java) or an sh or bash script, so building and releasing an app needs no second toolchain. Data files beside the scripts are not scripts. Editora meets it; Mirada, Modula and Torrenta each have Python scripts.

Performance

  • PERF-23 · MUST. Split out of PERF-06: work driven by text the user types waits for typing to pause when it leaves the FX thread or cannot finish within a frame, such as a search of files, a request to a server or a re-highlight. Filtering a list already in memory, as a command palette does, is exempt and runs on every keystroke, where PERF-06’s Check sent every listener on text through a debounce. Editora’s searches and its editor meet it; its debugger’s completion (ui/DebugCompletion.java) and ui/FileFinder.java do not yet.

Keyboard first

  • KBD-22 · SHOULD. The focus ring is 2 px wide at the default zoom and sits just outside the control with a 1 px gap, as a border with negative insets, so focusing a control never moves the layout. A text field and a control flush with the window’s edge draw it inside, at the same 2 px. Editora, Termina and Mirada already draw it this way; the app template sets the ring’s color only, so its ring is the theme’s 1 px border.

Window shell

  • WIN-12 · MUST. The app has a UI zoom: one setting scales the whole chrome (menus, toolbar, tabs, status bar), applies at once and is kept across launches, and three commands, with ids of the app’s own, zoom it in, out and back to the default. In an app with content to zoom, Ctrl+=, Ctrl+- and Ctrl+0 (Cmd on macOS) stay with the content zoom and the UI zoom’s commands have no fixed chord; in an app without, those chords are the UI zoom’s. This was the UI half of WIN-09, a SHOULD; no app has a UI zoom yet.
  • WIN-13 · MUST. Every quit entry point an app has runs one quit method: the Quit row, the app.quit command and the system’s own Quit, which on macOS is the application menu’s and the Dock’s; the method asks what CONF-01 requires, closes open dialogs and runs the save that closing the window runs. TRAY-04 asked this of tray apps only, and keeps the tray’s Quit. The app template and Mirada meet it; macOS’s Quit does not reach the quit method of Editora, Torrenta, Modula or nux, and Termina, with several windows, has no quit method.
  • WIN-14 · MUST. Every app has a Quit on every OS: the app.quit command, listed in the Command Palette, and, where the app has a File menu or a main menu (a menu button that holds the app’s commands as a menu bar would, such as Mirada’s ☰), a Quit row in that menu that runs the command. An app with neither menu meets the rule with the command alone, and closing the last window is never the only way out. The app template, Editora and nux meet it; Torrenta has the row but registers the command as quit, Termina and Mirada have no Quit, and Modula quits only from its tray and its window’s close button. The six rules that lean on a Help submenu of the app’s main menu (DIAG-10, DOCS-06 to DOCS-08, ABOUT-01, PWIN-01) link WIN-14 for what a main menu is.
  • WIN-15 · SHOULD. On macOS, Settings is in the application menu and runs the same command as the Settings row on Windows and Linux. Its title carries the chord the active keymap binds to that command, and the item gets no key equivalent of its own. No app meets it yet: Mirada has the item, with a fixed Cmd+, key equivalent, Termina adds About only, and the other apps add nothing to that menu.

Toolbars and tooltips

  • TBAR-14 · SHOULD. Every tooltip shows after the same 400 ms delay, set in one place: the factory that makes the app’s tooltips, or the stylesheet’s .tooltip rule. No app meets it yet: Termina is nearest, with one tooltip that sets no delay; Editora sets 300, 350 or 400 ms on some and Mirada 250 ms on one; the app template, Torrenta, Modula and nux set none.
  • TBAR-15 · SHOULD. The first of five rules in a new section, The main toolbar, for an app whose toolbar is a band of its own across the top of the main window: Editora’s and Torrenta’s ToolBar, not Mirada’s header buttons or nux’s bar of labeled buttons. The icon cluster and the pinned tail (Settings and the other controls the user must always reach) are separate containers, so a narrow window overflows the cluster’s icons and the tail keeps every control. Editora meets it; Torrenta keeps Simple mode and Settings inside its ToolBar, where they are the first to overflow.
  • TBAR-16 · SHOULD. In an app with a main toolbar, Settings closes the bar at its right end, with the Simple mode toggle just before it where the app has Simple mode, whether the mode is on or off. Editora and Torrenta meet it.
  • TBAR-17 · SHOULD. A main toolbar button is disabled while its command can’t act (Save on a saved file, Undo with nothing to undo), and the events that change that state update it; nothing polls. Torrenta binds each button to its command’s state; Editora refreshes its built-in buttons, and the ones added from its catalog stay enabled.
  • TBAR-18 · SHOULD. A command hides the main toolbar and shows it again, and the choice is kept across launches. Editora (view.toggleToolbar) and Torrenta (toggle-toolbar) have it.
  • TBAR-19 · SHOULD. The main toolbar keeps its height when a control in it hides or shows, so the tabs and the content under it never move. Editora pins the row’s minimum height to its project switcher’s.

Menus

  • MENU-18 · SHOULD. The menu row’s metrics, which 5.0.0 kept in a table: at the default zoom a row is 34 px high, its icon column 22 px wide with 8 px to the title, and its chord starts at least 18 px after the title; the popup’s card has a radius of 8 and a shadow of radius 16 whose offset is at least its radius. Only Editora draws that card. Termina, Torrenta and the template have the row’s padding and keep their themes’ popup (radius 4, a shadow at offset 2), the template with an 18 px icon column and a 16 px chord margin; Mirada and nux take their AtlantaFX theme’s popup, and Modula draws its own (rows of 4 × 8, a shadow of radius 20 at offset 6).

Settings

  • SET-22 · MUST. A config file is written whole or not at all: to a temporary file beside it, then moved into place. A config file is any file the app writes as a whole and reads back as its state (the settings, the session state, a store of bookmarks or presets, what a sync engine keeps beside its clone). Three kinds of file are not one: a file the app only appends to, a file in a sync clone’s working tree, and a file the app writes for one run and deletes at exit, such as one that tells another process where this run listens (Editora’s mcp-endpoint.json). Every app’s settings store already does it. The template writes its configuration import and its sync/base.json in place.

Diagnostics and support

  • DIAG-11 · MUST. The problem report is redacted before it is shown: home paths, user names, e-mail addresses, credentials and tokens are replaced. Split out of DIAG-06. The five apps with a report (Editora, Termina, Torrenta, Mirada and the template) all do it, each with a test.
  • DIAG-12 · MUST. The Report a Problem window shows the report in a field the user can edit, and its submit action copies the report as edited to the clipboard and opens a GitHub issue prefilled from bug_report.yml; nothing is uploaded. Split out of DIAG-06. The same five apps do it. They differ in one thing the rule does not ask: only Termina sends its environment block as the user left it, and the other four fill the form’s environment field from the block as the app built it.
  • DIAG-13 · MUST. When the prefilled issue link would be longer than 7,500 characters, the report stays out of it and the form’s report field asks the user to paste from the clipboard. Split out of DIAG-06, which said “about 7,500”. Editora, Torrenta, Mirada and the template do it at that limit. Termina has the limit but leaves the form’s field empty, with the hint only in its own window.

Command line and launch

  • CLI-12 · MUST. An option the app does not know, with one dash or two, stops the launch: the app names it on standard error, says how to get help and exits with status 2 before the GUI starts. In an app that opens files named on its command line, a lone - and everything after -- are files. The JVM options a launcher can leave among the arguments (--add-exports, --add-opens, -p) are skipped with their values, in the = form too. No app does all of it: the template, Termina and Torrenta refuse the launcher’s options with the rest, Torrenta refuses - and -- as well, Mirada takes a single-dash option for a file, Editora skips every unknown option without a word, nux ignores all arguments but two, and Modula reads none.
  • CLI-13 · SHOULD. The short flags are the same in every app: -h for --help, and both -v and -V for --version. Termina and Torrenta take all three. Editora lacks -v, the template lacks -V, Mirada has no short flags, and Modula and nux take neither flag in any form.

Internationalization

  • INTL-14 · MUST. The app starts in the language the user chose in its settings, else in the system’s language when it ships a catalog for it, else in English. The locale that formats dates and numbers keeps the system’s region (the bare language only when the chosen language is not the system’s own). That locale is the JVM’s default once the app has started: the app sets it wherever it is not the locale the JVM started with, and the message catalog formats its values with it. Termina meets it, with a test, and so does Modula, which offers no language choice and leaves the JVM’s locale as the system set it. Torrenta’s and Mirada’s catalogs format with the bare language, Editora and Mirada set the bare language as the default, nux sets bare English when it has no catalog for the system’s language, and the template never sets the default and formats its messages with the bare language.

Confirm dialog

  • CONF-13 · MUST. In an app that asks before a destructive action, every such question has one default button, and it is never the red one: Cancel where the only action is destructive, Save where saving is an option. The dialog opens with keyboard focus on it, so Enter in a question that has just opened destroys nothing, on every OS. The Check asks that Cancel, or Save, is made the default button and the destructive action’s default is unset, both before the dialog is shown: JavaFX gives the opening focus to the one default button. Termina’s close-running-program question and nux’s risky-command question meet it, as do about twenty of Editora’s, each set by hand. Editora’s Git confirmations and Local History purges, Torrenta’s RemoveConfirm, Mirada’s Confirm, the app template’s Confirm and Termina’s removals and its Import configuration leave the red action as the default; Torrenta’s four Settings questions leave OK as the default, and so do the questions of Editora’s that keep the stock OK, its delete to the trash, Revert and Save As overwrite among them; and Editora’s unsaved-changes and Quit questions have no default button.
  • CONF-14 · MUST. Every dialog with two or more buttons words each button from the message catalog, never with JavaFX’s stock OK, Yes, No, Cancel, Apply or Close, which are worded in the JVM’s locale. That is every JavaFX Dialog the app shows: a question, before a destructive action or not, a text prompt, a pick from a list, a form. Only a message with one button is outside. 5.0.0 said it of a confirmation, in the Confirm dialog’s Spec table only; CONF-03 keeps the verb in red. A button whose text is set from the catalog before the dialog is shown passes, and so does a dialog whose stock buttons are swapped for catalog-worded ones. Torrenta meets it, its text prompts and picks included, and Modula, whose one dialog is a message with one button, has nothing to judge. Termina, Mirada and the template meet it in their questions and not in their text prompts: Termina’s Rename Tab keeps the stock Cancel, and the prompt of its setting commands and Create on GitHub the stock OK and Cancel; Mirada’s Rename prompt keeps the stock pair; so do the template’s prompts, and its Report a Problem form keeps a stock Cancel. Editora does not: 26 of its 64 CONFIRMATION alerts keep the stock OK and Cancel, 22 more, the helper of its Git confirmations among them, name the action beside a stock Cancel, its warnings that ask do the same (its four trust questions, and the question before its MCP server is enabled), and so do its prompts and forms. Nor does nux, in any of its four dialogs of two buttons: the question before a risky command names Run beside a stock Cancel, and the question before a harmless command, the credentials form and the Save Profile prompt keep the stock OK and Cancel.

Find bar

  • FIND-16 · MUST. A control of a find bar or of a filter box leaves the Tab order only when the keyboard does its work another way: a registered command, or a key the bar’s own field handles. So Next, Previous and Close may leave it (Enter, Shift+Enter and Escape in the field do the same), and so may a field’s clear button. An option’s toggle (match case, whole word, regular expression) stays in it unless a command toggles the option, in a terminal’s bar as in any other. An app with no find bar and no filter box has no such control and passes. Termina’s regex toggle, out of the Tab order with no command, does not meet it yet, and fails KBD-15 with it.

Packaging, signing and release

  • REL-30 · MUST. A release is cut only from a commit whose tests passed: the release workflow runs the suite before it builds the installers, or a preflight job reads CI’s result for the tagged commit and stops when it is not green. All seven release workflows meet it: Editora’s and Torrenta’s read CI, and the template’s, Termina’s, Mirada’s, Modula’s and nux’s run the suite.
  • REL-31 · MUST. Every workflow that runs on pull requests has a concurrency group that cancels a superseded pull-request run, and never a run on the default branch, whatever starts it: a push, a schedule, or a run started by hand. The requirement was half of REL-26 in 5.0.0, whose Check passed a workflow with no group; REL-26 keeps the timeouts. The template, Termina and Mirada meet it, and so do Editora’s ci.yml and full-tests.yml. Editora’s third pull-request workflow, terminal-image.yml, does not: its cancel-in-progress is plain true and it can be started by hand, so a second run started on master cancels the first. Modula’s build.yml and nux’s ci.yml have no group, and Torrenta’s ci.yml cancels its pushes to master too.

Changed

Reading a rule

  • Which names in a statement are required as spelled. A command id, a catalog key, a chord, a command-line flag, an environment variable, a property in pom.xml or pauta.json, and a file the repository must carry: a document at its root, or a resource or tool configuration the rule names (AGENTS.md, emacs.json, messages_<code>.properties, jreleaser.yml). A user, the docs or another tool finds the thing by that name, so the same thing under another name fails the rule. A platform API a statement names (javafx.stage.Popup, SystemTray, Future.get()) is the requirement itself. Every other name is Editora’s spelling, and an app’s equivalent meets the rule: a class, method or constant of the app’s own code, a CSS file or style class, a branch or workflow file, a file the app writes as it runs (its config files), and any name that only a Check or a Reference gives. 5.0.0’s list was “a command id, catalog key, file, property or style class”: a style class, a stylesheet’s name, a config file’s name and the default branch’s name are no longer required as spelled, and chords, flags and environment variables are on the list by name. The Coding agents page, llms.txt and the audit skill state the same list.
  • A rule about a feature covers the apps that have it. 83 rules sit under an Applies to line, 25 in 5.0.0: the sections on the menu bar, right-click menus, tabs, tool panels, tool window stripes, the toolbar, the main toolbar, the QuickOpen picker and Settings Sync now open with one, and most say what counts as the feature (a right-click menu, tabs, a tool panel, a toolbar, a picker). Other rules name the apps they cover in their own words (“An app that stores a secret…”). An app outside a rule’s scope gets limited and owes no exception; a pauta.json entry for such a rule is a problem to remove (PAUTA-05). 28 of the app template’s 44 not-applicable entries are for rules that gained an Applies to line. A scope is written in the statement, in an Applies to line or in the rule it details, and nowhere else: an audit never infers one from what the app lacks.
  • A test is required only where the statement asks for one. 13 rules have a Check (test), 87 in 5.0.0. Five end “A test holds it.” (ACC-01, ICON-09 to ICON-12) and eight name the test in their own words (OS-03, PAUTA-10, QUAL-04, QUAL-11, QUAL-13, QUAL-15, PERF-21, ICON-23). 72 rules whose Check was a named test are now checked by reading the code: the Check describes the behavior to find and may end “A test that asserts it is the surest evidence”, and an app without that test still meets the rule. An app that met 5.0.0 does nothing; an app that failed one of these rules only for the missing test now meets it.
  • Each statement reads alone. An agent gets one rule from rules.json with no page around it, so a statement opens with its subject (“The Pauta window reads…”, never “It reads…”), the seven rules that depend on a Help menu say “where the app has a Help menu”, and no statement, Why, Check or Reference points at “the table above”: it says what it means or links the section. Where a statement or a Check links a section of its own page, as OS-01 and OS-04 link the table of allowed differences, the audit skill reads that section before it judges the rule. A statement reworded for this alone asks nothing new.

Auditing an app

  • A by-hand rule can fail on the source. The source cannot confirm a rule checked by hand, so an audit never passes one, but it can refute one: where the feature isn’t there at all, or the code plainly does otherwise (a Settings window built as a TabPane with no search field has no sidebar of pages), the rule is fail, with the file:line. A by-hand rule the app’s pauta.json lists as an exception gets that kind, not manual. Only what the source leaves open is manual. 39 rules are checked by hand, 43 in 5.0.0.
  • Each rule is judged on its own words. One defect that breaks two rules fails both, each with its evidence: a button that no command reaches and that is also out of the Tab order fails KBD-01 and KBD-15.
  • What a rule gets when the app has nothing of its subject. The rule’s own Check comes first: where it says what an app without the thing gets (“fails with FIND-01”, “is outside the rule”), that is the answer. Otherwise the skill takes the first of these that fits. The rule is limited and the app is outside it: limited. The rule says how a part behaves that another rule requires (the Debug Log’s find bar, the Pauta window, the keymap files, About’s edition link): it fails with the rule that requires the part, and its evidence names that rule, so one missing part reads as one cause. A rule worded as a limit on every item of a kind belongs here whenever some rule requires the app to have one: KBD-21 fails with KBD-09, ABOUT-06 with ABOUT-05. The rule constrains things no rule requires an app to have (“every deviation entry names a SHOULD”): with none of them it passes, which 5.0.0 did not say. Anything else is fail, and the fix is a not-applicable entry. An app with no pauta.json at all fails PAUTA-01 and PAUTA-09, and passes the rules about entries it does not have.
  • A search inside a Check is not a Command. A grep written in a Check’s own sentence, as in PERF-01 and OS-04, lists candidate lines for the auditor to judge one by one, and its exit code is no verdict; only a *Command:* settles a rule by its exit code. Where the candidates are too many to read, the evidence says how far the audit read, and the rule fails only on a violation found and cited.
  • Twelve Commands, as in 5.0.0. A *Command:* is one POSIX sh -c command, run from the app’s repository root, that exits 0 when the whole Check passes and prints what it found when it fails; the auditor still reads the rule and cites the file:line. REPO-11, a new rule, has one, KBD-09 lost its, and seven of the other eleven were rewritten (OS-02, PLAT-01, PLAT-09, PLAT-10, PLAT-13, KBD-10, REL-22).
  • The report and its schemas. The Markdown report has a not-checked column and a Not checked section, its Manual checks give each rule’s recorded edition and date or “not recorded”, and it closes by offering to settle the not-checked rules that a checked-out website or gh would reach. In audit.schema.json a result’s status may be not-checked, a manual result may carry checked (edition, date, optional version), and problem covers a stale checked entry and one for a rule that also has an exception. In rules.schema.json every rule requires changed.
  • The skill is the edition’s own. Audit with the copy of the skill the app’s edition serves, and replace an app’s own copy (.claude/skills/pauta-audit/) when the app moves to a newer edition (PAUTA-11). That copy decides how to audit and how to write the report, rules.json supplies the rules, and where an edition’s llms.txt says it differently the skill wins. For an app on 5.0.0 the skill judges names by 5.0.0’s list.

Editions and Pauta Next

  • The current edition while a batch waits. Every push to master now deploys. With changes waiting, latest/ and <version>/ are built from the last commit before the batch began (the release commit, or a later one that changed only the site) with the current build scripts, and master goes to next/. A fix to how the PDF or the Markdown download is made reaches the current edition at once. Its pages and agent files stay as released: a fix to them made once a batch waits shows in next/ at once and in an edition at the next release. In 5.0.0 a push made while a batch waited deployed nothing, unless the current edition was not live yet.
  • The Markdown download reads as the pages’ Markdown does. Each mockup in adl-desktop-apps-guidelines.md is a sentence saying what it shows, its numbered parts a list, as in <page>.md. It was the mockup’s HTML.
  • PDFs of the two newest editions. The site serves the PDF of the two newest editions; an older edition’s overview links its PDF on the versions branch on GitHub.

The family pages and the checklist

  • New app checklist. 143 lines, 118 in 5.0.0, 26 of them marked SHOULD. Every new MUST and every new SHOULD has a line, the lines follow the four level changes (PLAT-02 and QUAL-05 on lines marked SHOULD, ICON-09 on a MUST line with ICON-14 on a SHOULD line of its own, REL-20 unmarked), the retired IDs are gone, and a line about a feature says which apps it covers (“In an app with a menu bar…”).
  • Coding agents and LLMs. The page states the names list, shows a rule with changed, has the not-checked status and the checked list in its table, sample report and reading notes, and gives the move to a newer edition as four steps: replace pauta-rules.json and the app’s copy of the skill, remove the checked entries the new edition makes stale, meet or record each new MUST and audit again, then change pauta.version, AGENTS.md and the README together.
  • Principles. Principle 5, the UI never waits, names the two exceptions PERF-01 allows: at start-up, before the first window is shown, the wait for the config read and the reading of the bundled resources that window is built from (its fonts, the message catalog, the keymap, its icons); and the last save as the app quits.

Same on every OS

  • OS-02 · MUST. 5.0.0 asked for one class named Os, with isWindows(), isMac() and isLinux(), as the only reader of os.name. The names are now the app’s own, and the statement adds that a class which only shows the OS’s name, in About or a problem report, asks that one class for it. The Command also fails a class that tells the OS apart by comparing File.separatorChar or File.pathSeparatorChar with a character, as eleven of Editora’s classes do. No app meets the rule yet; OS-03 follows the wording.
  • The table Where the OS’s way wins. Its rows are the only exceptions OS-01 and OS-04 allow, and eight were added since 5.0.0: a click with the primary modifier, Enter on a focused button that is not the default, the macOS application menu, files opened from the OS, file associations, the Trash, the shells and profiles a terminal offers, and high contrast. The “Primary modifier” row is now “Keymap chords”: on macOS, the .mac.json variant of each keymap that has one, as KBD-21 allows, not Cmd for Ctrl alone. The Quit row cites WIN-14 and WIN-13 beside TRAY-04, and the Menu bar row no longer says “in a decorated window”. A difference that a new row gives no longer breaks OS-01 or OS-04.

Conformance

  • PAUTA-02 · MUST. The conformance is still computed from the exceptions by one pure helper; the statement adds that nothing else enters it: the checked list (PAUTA-18) is a record, and a by-hand rule with no entry there leaves the result as it is. The Check reads the helper and no longer asks for its unit test. The test that holds the README’s badge and line to the computed conformance is still required. Nothing to do for an app that met 5.0.0.
  • PAUTA-03 · MUST. 5.0.0 said “a new app’s first release is at Core or Complete”. The statement now says which app that is: one that has made no release yet, with no numbered section in its CHANGELOG.md and no version tag. An app with a release behind it is outside the rule: it may be at Partial, and says so.
  • PAUTA-04 · MUST. 5.0.0 asked that a person check every by-hand rule in the running app before the conformance was claimed. Now a by-hand rule counts once a person has checked it: found unmet it gets an exception, found met a checked entry (PAUTA-18), and until then it has neither, which is not a failed audit. The audit reports it as manual, not recorded, and a not-checked result fails nothing either. The Check is the audit itself, which judges this rule last from its other results; nothing to do for an app that met 5.0.0.
  • PAUTA-05 · MUST. The three things that limit a rule to apps with a feature are unchanged: its own text, an Applies to line, or a limited rule it details. The statement adds that nothing else limits one, so a scope is never inferred from what the app lacks. An app that left out an entry on that ground alone records not-applicable.
  • PAUTA-09 · MUST. pauta.json is now the one source of the record of by-hand checks as well as of the exceptions, and the statement names its place, among the app’s bundled resources (src/main/resources/com/<app>/pauta.json). The checked list is the app’s to keep or not, and what an entry of it holds is PAUTA-18’s alone. A file with no checked list passes, so an app that met 5.0.0 has nothing to do.
  • PAUTA-10 · MUST. The test gains the failures of a checked entry: one that names a rule not checked by hand, a rule listed twice, a rule that has an exception, an edition newer than pauta.version, or an edition older than the rule’s changed, which makes it stale. The Check asks for a case for each failure the rule lists, so an app that met 5.0.0 adds those cases. The repository the test compares a pending link with is the one the app’s own code names; AppInfo.GITHUB_REPO is the template’s name. The template’s test reads the exceptions list only so far.
  • PAUTA-11 · SHOULD. Moving to a newer edition gains two steps: replace the app’s copy of the audit skill where it keeps one (the template’s is .claude/skills/pauta-audit/SKILL.md), and remove the checked entries the new rules.json makes stale, then check those rules again. Nothing fails a skill copy left behind, which then audits the new rules by the old procedure.
  • PAUTA-13 · MUST. 5.0.0 ended with “The Pauta window links to it”. That link is PWIN-07’s alone, a SHOULD, and PAUTA-13 keeps the Pauta conformance page on the website. Its Check starts in the app’s checkout: an app whose repository and About name no website for its user docs has nowhere to carry the page, and fails. The rest reads the website’s repository (<app>-website): the page gives the edition, the conformance and every exception under its kind, each with its rule ID, reason and link. An audit run from the app’s checkout alone reports that part as not-checked and says what would settle it.
  • PAUTA-16 · MUST. The rule now says whom it leaves out: an app that was not made from a template inherits nothing, and the rule asks nothing of it; an audit reports it as limited. For a template and the app made from one it asks what 5.0.0 did. Nothing builds it yet: the template’s pauta.json has no template field, its script sets none, and its test accepts a pending link to the template’s own repository.
  • PAUTA-17 · MUST. 5.0.0 required a ## Pauta section in AGENTS.md. The heading is now the app’s own: a section on Pauta that names the edition pauta.version names and links that edition’s llms.txt and llms-full.txt at its numbered address, never latest/. The Check reads the file for both links, where it had asked a test for the first alone, and no longer requires a test. The template, Termina and Mirada have the section (5.0.0’s Reference left Mirada out); Editora’s and nux’s AGENTS.md have none, and Torrenta and Modula have no AGENTS.md.

Platform baseline

  • PLAT-01 · MUST. 5.0.0 said CI builds and bundles JDK 25, and its Check demanded an enforcer rule with the range [25,). Now no enforcer rule is required, but none may refuse a newer JDK, in the main build or in any profile that turns itself on: one with an <activation> by JDK version, OS, property or file, or one that is activeByDefault. A profile turned on only by name with -P is not counted. Every workflow step that sets up a JDK sets up release 25, and a native-image leg sets up a GraalVM 25.x release. The Command reads the workflows and those profiles too, leaves XML comments out and judges every version key of a set-up step. A floor of 26 no longer passes it, and any range with no upper bound that starts at 25 or below does, such as [21,) or a bare 25. Modula and nux, with no enforcer rule, now pass and Torrenta’s [25,26) still fails; Editora, which passed, now fails for its formatter-needs-jdk25 profile, which activates on JDK 26 or newer and holds an enforcer rule with the range [25,26). No app’s profile that activates by OS, property or file holds an enforcer rule, and no app has an activeByDefault profile.
  • PLAT-02 · SHOULD. A MUST in 5.0.0: a jlinked runtime in every installer is now expected, not required. Mirada ships a GraalVM native image on every target but Intel macOS, with no Java runtime in it, and its users still install nothing. The Check adds that the jlinked image is what the release ships.
  • PLAT-04 · MUST. 5.0.0 required the module name com.<app>. The name is now the app’s to choose (the template’s is com.example.app): the rule asks for one named module, not an open module, whose module-info.java opens only what reflection, FXML and Jackson need. Nothing to do for an app that met 5.0.0.
  • PLAT-10 · MUST. 5.0.0 asked that CI fail an unformatted change, and its Check accepted Spotless’s check goal bound to a phase a workflow runs. Termina, Torrenta, Modula and nux, which have no TestFX dependency, no longer fail the rule for that.

The Check asks for an execution of JaCoCo’s check goal, whatever its id. The rule is about the pom’s profiles: a workflow that runs the tests on some of its runners with JaCoCo skipped (-Djacoco.skip), as Editora’s full-tests.yml does, is the workflow’s choice and passes. Termina, which met 5.0.0, has its os-windows profile to redo: it lowers the two floors to 0.45 and 0.47 on Windows.

Repository documents

Documentation

  • DOCS-02 · MUST. The frontmatter keys category and order were required as spelled and are now editora-website’s: a docs page gives its category and its place in it. Nothing to do there. Editora’s docs/plugins.md, a page for plugin authors with a section on installing plugins and one on troubleshooting them, is one; so are Termina’s docs/reference/installing.md, which tells the person installing it which download to take and how to check its signature, and Torrenta’s three guides. Editora, whose notes are built from the commits, and Modula and nux, which have GitHub generate them, have this to redo. A row beside a Help submenu is not in it, which is where Mirada’s main menu has it; its macOS Help menu has the row. Modula and nux have no documentation command.

The rule covers an app with a Help menu, in a menu bar or as a submenu of its main menu, and an app with both is judged on both. Termina’s menu and Mirada’s macOS menu bar have the keyboard reference in its place. Now, where the app has a Help menu, a row of it opens the reference: a searchable window of every key, or the keybinding editor. Termina has the row; Mirada has it in its macOS Help menu, and beside the Help submenu in its main menu.   • TABS-09 · SHOULD. 5.0.0 wrote the switcher’s keys as Emacs chords (C-x C-b, C-n, C-p, C-g, C-d).   • TABS-13 · MUST.   • TABS-16 to TABS-18 and TABS-20 to TABS-23. Menus

  • MENU-01 to MENU-04 and MENU-17. The menu bar’s rules apply to an app with a menu bar, so Modula and nux, which have none, record nothing for them. MENU-04 covers only an app with a Simple mode.

Rows of Torrenta’s View menu are built that way, and Termina’s bar holds rows that are no command id: its New Tab With Profile submenu, whose rows open the tab from a handler of their own, and, off macOS, its zoom row.
  • MENU-05 to MENU-13. The right-click menus’ rules apply to an app with a right-click menu: one the app builds and opens on a right-click, the Menu key or Shift+F10. The stock Cut, Copy and Paste menu of a text field and a tray icon’s menu do not count, so nux is outside these rules.

What must have a menu is said too: the lists, trees, tabs, editors and read-only consoles in the app’s windows. A log shown as text, the Debug Log among them, is a read-only console and has its menu; a list that only navigates (a Settings sidebar, a list of pages) has no actions of its own and is outside, as are the overlay list of a picker or a palette and a plain text area in a dialog. The reference is the template’s CommandMenu, which builds each menu from command ids. Five apps don’t meet it, in these places among others. Editora’s menus are built by hand and call the window’s methods, so nothing holds that each row has a command, and its Hierarchy, References and Undo History panels have no menu. The Message Log’s list has none in Termina or in Mirada, and the Debug Log’s text has none in Editora, Torrenta, Termina or Mirada; the template’s has one. Rows of Torrenta’s files and peers menus run handlers no command reaches, and in Modula the Rename… and Remove rows of a preset chip’s menu run none.
  • MENU-09 · MUST. Adds two things: in a view with no rows (an editor, a terminal, an image) the Menu key and Shift+F10 open the focused view’s menu, and on macOS the chord is Shift+F10 too, with no Cmd form. Editora’s IntelliJ keymap also binds S-f10 to run.rerun, a clash its test does not cover.
  • MENU-12 · SHOULD. A destructive row has its text in -color-danger-fg; danger is Editora’s style class for it and no longer required. The rule asks for that style alone: what the action does before it destroys anything is the Confirm dialog’s (CONF-01, CONF-03), where 5.0.0 pointed at the window shell. Nothing to do for an app that met 5.0.0.
  • MENU-15 · MUST. Covers every menu the app draws itself: right-click menus, drop-downs and the toolbar’s overflow as the in-window menu bar. The menus a platform draws are outside it: the macOS system menu bar, whose rows carry the chord in their title (MENU-02), and a tray icon’s menu. The chord is drawn in the app’s keyboard color, the one color it keeps for chords and key chips (ICON-06), at the size MENU-16 gives; -state-key is Editora’s token for that color and no longer required as spelled. The Check accepts, outside the menu bar, the item’s accelerator text filled from the keymap, and passes an app whose menu rows run only commands that have no chord, as nux’s drop-downs do. The template and Termina’s menu bar draw the chord in -color-fg-muted and fail on the color; Editora’s right-click menus still show no chords.
  • MENU-16 · MUST. Covers every menu the app draws itself (the in-window menu bar, right-click menus, the drop-down of a menu button or a split button, the toolbar’s overflow), not the macOS system menu bar or a tray icon’s menu, which are the platform’s. Menu fonts scale with the UI zoom of WIN-12, which every app must now have; 5.0.0 pointed at WIN-09, where the UI zoom was a SHOULD. The 14 px and 11 px come from one value that the zoom rewrites, in pixels and never in em. Editora writes them as fixed pixels and has no UI zoom yet.
  • MENU-17 · SHOULD. Covers the in-window menu bar an app shows on Windows and Linux: a keymap that binds F10 to something else binds a command that focuses the bar, and so does a terminal app, where a plain F10 goes to the program it runs. The macOS system menu bar asks nothing of the app, and 5.0.0’s Ctrl+F10 there is dropped. No app has the command yet.

Tray and background

  • TRAY-01 · MUST. The tray is a StatusNotifierItem on Linux with no AWT fallback, and AWT’s SystemTray on Windows and macOS, created on a background thread no sooner than the code that shows the main window. 5.0.0 asked for “the shared tray/ package”, which was three diverged copies, and for creation after the first frame. Torrenta meets it. Modula and nux fall back to AwtTray on Linux and have the fallback to remove.
  • TRAY-02 · MUST. When no icon comes up, the main window’s status line says why and that closing the window quits the app; 5.0.0 said “where the person will look”. Torrenta does, Modula’s status says that closing will quit, and nux shows the window and says nothing.
  • TRAY-04 · MUST. Keeps the tray’s part of the quit rule: the tray’s Quit runs the app’s one quit method, and a quit ends the program whether the window is showing or hidden, never hiding it as a close would. That every quit entry point runs the one method, which closes open dialogs first, is now WIN-13’s, for every app. Nothing to do for an app that met 5.0.0. No tray app catches macOS’s Quit yet, and Modula’s and nux’s quit does not close open dialogs first.
  • TRAY-05 · SHOULD. With the tray setting off, --minimized starts the window minimized. 5.0.0 wrote two behaviors into the rule, Torrenta’s minimized window and nux’s ignoring the flag; nux now has Torrenta’s to adopt. With the setting on nothing changes: the window waits for the tray attempt and is shown if no icon comes. Modula has no --minimized.
  • TRAY-09 · MUST. The text reaches the notifier’s program as data, an argument or an environment variable that a fixed script reads, where 5.0.0 allowed arguments only. The call times out after ten seconds or less, where 5.0.0 said “a few seconds”: Editora, Termina and nux kill the program after five seconds and Torrenta after ten, so all four are within it. A gdbus fallback on Linux is allowed and not asked for, and the class need not be named Notifier. The Check reads the code and also tests the timeout and that a failure is logged: an exception, a program that is not there to run, the timeout, and an exit code that is not zero. No app logs them all: Termina logs an exception only, Editora drops a failure unlogged, Torrenta reports only the first of a session, and nux logs none, builds an AppleScript string on macOS and shows AWT’s balloon on Windows in place of a PowerShell toast.
  • TRAY-10 · MUST. Says outright that nothing is posted for an event whose window, or tab, is the one in front, and asks that most switches start off only where the app notifies of several kinds of event. Editora and Termina, with one kind and one switch, meet it. Torrenta posts while its window has focus, and nux posts while in front and has one switch for all its power events.
  • TRAY-12 · MAY. Written for any app’s dock badge, where 5.0.0 described Torrenta’s: a figure of the app’s own on the macOS dock icon and on a Linux launcher that honors Unity’s LauncherEntry signal, nothing on Windows, cleared when there is nothing to show, with a switch of its own.
  • TRAY-14 · SHOULD. Keeps only the tray’s part: a tray makes AWT headful on Windows and macOS and never on Linux, and a tray turned on after start-up tells the user to restart. The list of uses that may make AWT headful, and that main decides once, is CLI-09’s. Nothing to do for an app that met 5.0.0; Modula and nux never set java.awt.headless.

Settings

  • SET-01 · MUST. Termina, Torrenta and nux bind it; Modula’s Settings command has no chord.

  • SET-07 · MUST. Says that the default ~/.<app> is in the user’s home on Windows, macOS and Linux alike, and which source wins: --config-dir, then --dev, then <APP>_CONFIG_DIR. No app has all of it. In Editora, Termina and the template the variable beats --dev; in Mirada the flag typed last wins and the default folder depends on the OS; Torrenta has no --dev; Modula and nux read a fixed folder, with no flag and no variable.

  • SET-09 · MUST. Every config file the app writes and reads back (SET-22 says which files those are) carries a schema version, with a migration step for each version; 5.0.0 said “every versioned file”, which an app with none could pass. A plain list with one item to a line is exempt, and SCHEMA_VERSION is Editora’s name. Torrenta’s and Modula’s files carry no version, nux writes one it never reads, the template’s sync/base.json has none, and nor have the color schemes Termina imports, each a file it writes whole and reads back at start.

Torrenta, Modula and nux read no version, so they cannot tell a newer file until they meet SET-09, and nor can Termina for an imported color scheme.
  • SET-13 · MUST. Covers an app that stores a secret the user gave it (a password, a token, a key): each goes to the OS keychain and none to a config file, where 5.0.0 named API keys and tokens. It says what happens when no keychain answers: the secret is kept in memory for the session, never written to a file, and its Settings row says so, as a line on standard error does in a run with no window. A key or token the app generates itself is not such a secret: it may live in a file only the owner can read, outside the settings files, as Torrenta’s keys/<name>.key and the token in Editora’s mcp-endpoint.json do. Whether a credential is kept from one session to the next is the app’s to decide: one it keeps is this rule’s, and one it only holds for the session is SET-14’s. Editora’s fallback writes its AI keys to the settings, and Torrenta keeps its proxy, certificate-file and remote-profile passwords and its Torznab keys in plain text. Termina, Mirada and Modula store no secret and are outside the rule.
  • SET-14 · MUST. Covers a credential the app asks for and does not keep from one session to the next, where 5.0.0 said “a credential the app can ask for again”: it is held in memory for the session and never written. Whether to keep a credential is the app’s to decide, and one it keeps is SET-13’s alone, as Torrenta’s proxy and remote-profile passwords are. nux’s UPS login and the SSH passwords and key passphrases Editora asks for are what the rule covers today, and both apps meet it. An app that asks for no credential, or keeps every one it asks for, is outside it, as Termina, Mirada and Modula are. Nothing to do for an app that met 5.0.0.
  • SET-15 and SET-18 to SET-21. These apply to an app with Settings Sync, SET-15 by its own words and the others by their section’s scope. An app without Settings Sync records nothing for them. SET-15 says what the refusal tells the user to use instead, a Git credential helper or an SSH URL, where 5.0.0 said “with the fix”.
  • SET-16 · MUST. Says what weakens security: an option that switches off a check or a question the app otherwise makes to protect the user. A feature, such as remote access or a proxy, is not such an option. Nothing to do for an app that met 5.0.0.

Menus

Two surfaces show the same rows: the menu bar, a browsable map of every command, and right-click menus, what can be done with the thing under the pointer. Both are built from the command registry, so a row’s title, icon, chord and enabled state come from the command and never drift from the palette or the toolbar. Reference: Editora’s ui/MainMenuBar.java (menu bar), ui/ContextMenuDismissal.java, ui/LazyContextMenu.java, ui/RowContextMenu.java and ui/TabContextMenu.java (right-click menus), and the .menu-item and .context-menu rules in app.css.

Look and feel

Section titled “Look and feel”

Both surfaces draw their rows the same way. Absolute pixels are deliberate: a popup inherits the font of the node it was opened from, and em would resolve against a file tree’s or an 18 px toolbar’s size (Editora’s toolbar menu once rendered a third larger than every other menu in the app).

The shadow’s offset is not cosmetic. A menu is a native window sized to its root including the effect, so a shadow that reaches above the menu is invisible window over the bar the menu hangs from, and the pointer lands on it instead of the next menu button. The offset must be at least the radius; Editora pins it with MenuPopupBoundsFxTest.

The three rules below hold for every menu the app draws itself: the menu bar, right-click menus, the drop-down of a menu button or a split button, and the toolbar’s overflow. The menus a platform draws (the macOS system menu bar, a tray icon’s menu) show text only; there the chord is appended to the title (MENU-02) and the tray shows neither.

  • MENU-14 MUST Every row of every menu the app draws carries an icon that depicts it. A command row wears its command’s glyph; a row that names a thing rather than an action (a recent file, a branch, a project) wears that thing’s icon; a submenu wears its family’s. Only a check or radio row goes without, because its mark fills the icon column. Where the icon set has no glyph that depicts a command, the app adds one (a Material 24 dp path, or a line glyph in the kit’s style) instead of leaving the row blank or borrowing another command’s.
    • Why: a menu is scanned before it is read, and the glyph is what the eye finds first; the same glyph on the toolbar, in the palette and in the menu (ICON-20) is learned once. A blank cell breaks the column, and a borrowed glyph says something else.
    • Check (test): an FX test opens the menu bar’s menus and the right-click menus of a tab, an editor, a list row and the toolbar, and fails on any visible row that is not a check or radio item and has no graphic.
    • Reference: Editora ui/MenuBarIcons.java, editor/MenuIcons.java, ui/TabContextMenu.java; Termina’s tab menu has an icon on every row. Editora doesn’t yet pass: about half its menu-bar rows have no glyph, and MenuBarIconsTest holds that a command without a fitting glyph gets none, which this rule reverses; many right-click and drop-down rows have none either (Run All Requests in a .http file, the CSV grid’s menu, the Markdown preview’s).
  • MENU-15 MUST Every menu row whose command has a chord in the active keymap shows it, in right-click menus and drop-downs as in the menu bar: right-aligned in the menu’s chord column, Inter 11 px in -state-key. An unbound command leaves the cell empty, never a wrong chord, and a keymap switch rewrites every cell.
    • Why: the menu is where a user learns the keys. A right-click menu that hides them teaches the mouse, while the palette and the toolbar’s tooltips already show the same chord.
    • Check (test): an FX test binds a command, opens a right-click menu that lists it and finds its chord in a menu-item-chord label; after a keymap switch it finds the new chord.
    • Reference: Editora MainMenuBar.rowContent and alignChordColumns, .menu-item-chord in app.css. Editora’s right-click menus show no chords yet: a row there is a plain MenuItem, not the menu bar’s row.
  • MENU-16 MUST Every menu draws its titles in Inter 14 px regular and its chords in Inter 11 px, whatever node it was opened from: the font is pinned in absolute pixels on .context-menu and its rows’ labels.
    • Why: a popup inherits the font of the node it was shown from, and em resolves against it: Editora’s toolbar menu once rendered at the bar’s 18 px, a third larger than every other menu, and a file tree’s or a monospace editor’s font leaks the same way.
    • Check (test): an FX test opens a menu from the toolbar, an editor and a tree row and reads Inter 14 px from each row’s title.
    • Reference: Editora .context-menu and .menu-item-chord in app.css, MainMenuBar.UI_FONT_SIZE, ToolbarMenuFontFxTest.

  1. 1Menu button. Padding 3 × 10 on a bar with 4 px side insets; the bar and the toolbar share one -color-bg-subtle band with no rule under it.
  2. 2Icon column, 22 px. Every row has a glyph that depicts its command; where the icon set has none that fits, the app adds one rather than leave the cell blank.
  3. 3Title, 14 px Inter, the command's title with the menu's own name dropped ("Save", not "File: Save") unless two rows would then read the same.
  4. 4Chord column. Inter 11 px, periwinkle, right-aligned into one column per menu (not app-wide), read from the active keymap. Drawn by the app, not a JavaFX accelerator: Emacs chords are multi-key, which a KeyCombination cannot express, and on macOS an accelerator would bypass the key dispatcher.
  5. 5Unbound command. An empty chord cell, never a wrong chord. A live keymap switch rewrites every cell.
  6. 6Submenu row. Icon, title and an invisible chord as wide as the menu's widest, so its arrow sits at the right edge instead of halfway across.
  7. 7Card. Radius 8; the shadow falls below the menu (offset ≥ radius), so nothing invisible covers the bar.
  • MENU-01 MUST Every menu-bar item is a command from the registry, with its title from command.<id>, its chord from the active keymap and its enabled state from the command’s gate. The bar assembles and refreshes; it holds no behavior of its own.
    • Check (code): the bar’s model lists command ids only, and every row runs its id through the registry.
    • Reference: Editora ui/MenuBarModel.java over command/CommandRegistry.java, ui/MainMenuBar.java.
  • MENU-02 MUST Menu-bar rows use no KeyCombination accelerators. In the in-window bar each row is a CustomMenuItem laying out icon, title, spacer and chord. On the macOS system menu bar (useSystemMenuBar) the chord is appended to the title and rows carry no icon.
    • Why: Emacs chords are multi-key, which a KeyCombination cannot express, and on macOS an accelerator would bypass the key dispatcher. The native macOS menu draws text only and no graphics, which is also the platform’s convention.
    • Check (code): no setAccelerator in the menu-bar classes.
    • Reference: Editora ui/MainMenuBar.java (rowContent, refresh).
  • MENU-03 SHOULD Enablement is re-read every time a menu opens, and titles and chords on a keymap or locale change.
    • Why: a menu built before Git finished detecting a repository must not stay grayed out.
    • Check (test): an FX test detects a repository after the window is built and finds the menu enabled.
    • Reference: Editora MainMenuBar.refreshEnablement, MenuBarEnablementFxTest.
  • MENU-04 SHOULD Simple mode shows a shorter menu, rebuilt only when the mode actually changes.
    • Check (code): the bar rebuilds only when the simple flag differs from the current one.
    • Reference: Editora MainMenuBar.setSimple, MenuBarModel.menus(simple).

Right-click menus

Section titled “Right-click menus”
  • MENU-05 MUST Every list row, tree row, tab, editor and read-only console has a right-click menu with the actions for that thing, each one a command.
    • Check (by hand): right-click each kind of thing; every row’s action is also in the palette.
    • Reference: Editora ui/TabContextMenu.java, ui/RowContextMenu.java, ui/ConsoleContextMenu.java.

Behavior

Section titled “Behavior”
  • MENU-06 MUST One right-click menu at a time: a right-click while a menu is open replaces it, and the first one closes before the second shows.
    • Why: JavaFX stacks a second menu beside the first when each row owns its own ContextMenu, and the stale one is then no longer dismissible.
    • Check (test): an FX test right-clicks another row with a menu open and finds one menu showing.
    • Reference: Editora ui/ContextMenuDismissal.java closes every open right-click menu on the press that opens the next (ContextMenuDismissalFxTest); Modula’s RadioPane hides the previous menu before showing a new one; Termina keeps one menu per view and shows it again.
  • MENU-07 MUST A press anywhere outside a right-click menu closes it, including inside the control the menu was opened on. The press is not consumed: a click in a list still selects the row, and a right-click on another row opens that row’s menu straight away. Drop-downs opened by a plain click (menu buttons, choice boxes, the menu bar) keep the stock behavior, and a menu that turned auto-hide off is left alone.
    • Why: JavaFX’s auto-hide deliberately ignores a press on the menu’s owner node, so a stock menu on a tree or a text area stays open when the user clicks another row or the text.
    • Check (test): an FX test clicks inside the owner control and in another window, and the menu closes.
    • Reference: Editora ContextMenuDismissal.install(), called once in App at startup for every current and future window; ContextMenuDismissalFxTest.
  • MENU-08 MUST Escape closes a right-click menu and focus goes back where it was. In a terminal the Escape does not reach the shell.
    • Check (by hand): open a menu, press Escape, and type: the keys reach the control that had focus.
    • Reference: the stock ContextMenu hide-on-Escape (Spec below); Termina’s onKeyPressed filter hides the menu and consumes the key (TerminalView).
  • MENU-09 MUST The Menu key and Shift+F10 open the selected row’s menu, scrolled into view first, so every row action a mouse can reach the keyboard can too.
    • Why: those keys arrive at the focused control, not at a row’s cell, so a menu installed on cells never saw them.
    • Check (test): an FX test sends a keyboard request to a tree and a list and finds the selected row’s menu, anchored to that row.
    • Reference: Editora RowContextMenu.install(tree), RowContextMenuFxTest.
  • MENU-10 SHOULD A right-click selects first. In an editor, a right-click outside every selection moves the caret to the click (so Paste lands there); inside a selection it keeps carets and selections (so Cut and Copy act on what was clicked). From the keyboard the target is the caret. In a list, the menu is the clicked row’s.
    • Check (by hand): select a word, right-click elsewhere and paste; then right-click inside a selection and copy.
    • Reference: Editora editor/ContextMenuTarget.java.
  • MENU-11 SHOULD A menu attached to something that exists once per open file is built when first shown, and set up for each showing: an onShowing handler sets the labels, enablement and visibility for this showing, then collapses the separators.
    • Why: such a menu is built for every file and opened for almost none.
    • Check (code): per-file menus are created through LazyContextMenu.of(build).
    • Reference: Editora ui/LazyContextMenu.java, LazyContextMenuFxTest. A read-only console’s menu is just Select All and Copy, both disabled while it is empty (ConsoleContextMenu).
  • MENU-12 SHOULD A destructive row carries the danger class. The action follows the window shell rule: it asks first with a button that names it, or is undoable.
    • Check (code): rows that delete, discard or reset add danger to their style classes.
    • Reference: Editora .menu-item.danger in app.css, ui/BranchPopup.java.
  • MENU-13 MAY In a terminal view, a program that grabbed the mouse owns the right-click; Shift+right-click always opens the menu, and the keyboard request is never contested.
    • Check (test): a pure test of when the menu shows, per mouse mode, Shift and trigger.
    • Reference: Termina’s TerminalView.shouldShowMenu, ContextMenuContentionTest.
